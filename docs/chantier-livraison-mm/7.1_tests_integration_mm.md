## 1. Ce qui a changé par rapport à la version originale de ce sprint

Trois différences structurelles avec la version monolithique d'origine,
vérifiées dans le code avant d'écrire ce guide :

1. **Il n'y a plus de login JWT interne.** `JwtUtil` et
   `AuthController.login()` ont été supprimés au Sprint MM.7 (décision de
   portée P-2) : Keycloak (conteneur local, `docker-compose.yml`, realm
   `dottel-dev`) est l'unique émetteur de jetons, via Authorization
   Code + PKCE côté frontend. Un test d'intégration ne peut donc plus
   obtenir un jeton par un simple `POST /auth/login`.

2. **Le décodeur JWT se construit au démarrage du contexte, pas à la
   première requête.** `spring.security.oauth2.resourceserver.jwt.issuer-uri`
   déclenche `JwtDecoders.fromIssuerLocation(...)`, qui interroge
   `/.well-known/openid-configuration` **dès la création du bean** —
   avant qu'un seul test ne s'exécute. Sans précaution, `@SpringBootTest`
   échouerait si le Keycloak local n'est pas démarré, ce qui romprait
   `mvn test` en CI ou sur un poste sans Docker lancé.

3. **`ModularityTests` et `DocumentationTests` existent déjà** (verts
   depuis MM.5, package `com.afriland.dottel`). Ce sprint ajoute une
   classe **nouvelle**, `IntegrationFluxMetierTest`, à côté — il ne
   modifie pas les deux existantes.

### 1.1 La solution retenue pour le point 2 : un `JwtDecoder` de test

Le module `spring-security-test` est déjà une dépendance du projet
(`pom.xml`). Il fournit
`SecurityMockMvcRequestPostProcessors.jwt()`, qui **injecte directement**
une `Authentication` dans le contexte de sécurité d'une requête `MockMvc` —
sans jamais appeler le vrai `JwtDecoder`. Cela ne suffit pas à lui seul :
tant qu'un bean `JwtDecoder` réel doit être construit au démarrage du
contexte, l'appel réseau vers Keycloak a déjà eu lieu.

La solution standard Spring : une `@TestConfiguration` qui déclare son
propre bean `JwtDecoder` (jamais réellement invoqué grâce à `.with(jwt())`,
mais présent pour que l'auto-configuration — conditionnée par
`@ConditionalOnMissingBean` — n'essaie pas de construire le sien). Ce point
est proposé comme **défaut technique recommandé**, pas comme une décision
métier : si la session live préfère une alternative (Keycloak réellement
démarré via `docker-compose up keycloak` avant `mvn test`, ou
`spring-security-test`'s `EmbeddedKafka`-like approche avec Testcontainers
Keycloak), c'est un choix d'implémentation qu'elle peut trancher seule.

### 1.3 Frontières où le mock est légitime

La consigne « pas de mocks » de l'original visait la logique métier et la
base de données — pas les systèmes externes que le projet ne contrôle pas.
Trois frontières où mocker/substituer reste cohérent avec l'esprit du
sprint :

- **`JwtDecoder`** — substitué par construction (point 1.1), Keycloak
  n'étant pas la responsabilité de ce module.
- **`KafkaTemplate`** (publication de l'événement de clôture,
  `EvenementClotureService`) — pas de dépendance `spring-kafka-test`/
  `@EmbeddedKafka` dans le projet actuellement. Utiliser `@MockBean
  KafkaTemplate` et vérifier `verify(kafkaTemplate).send(...)` avec le
  bon topic et le bon payload est suffisant pour prouver que
  l'événement est publié, sans exiger un broker réel pendant `mvn test`.
- **`NotificationService`** — l'implémentation par défaut
  (`dottel.notifications.enabled` absent) est déjà `NotificationServiceStub`,
  pas un envoi SMTP réel. `@MockBean NotificationService` pour vérifier
  les appels reste la manière la plus directe de prouver qu'un événement
  a bien déclenché une notification, sans dépendre du timing
  `AFTER_COMMIT` dans un test `@Transactional` classique (voir point 1.4).

Tout le reste — état des entités en base, transitions de statut,
contraintes SQL, séparation des tâches, unicité — reste testé sans aucun
mock, contre PostgreSQL réel, comme dans l'original.

### 1.4 Piège `@Transactional` + `AFTER_COMMIT`

`@Transactional` sur une méthode de test fait généralement tout retomber en
rollback à la fin — mais un `@TransactionalEventListener(phase =
AFTER_COMMIT)` ne se déclenche **jamais** si la transaction du test ne
commite jamais réellement. Le test du flux notifications (étape 5) doit
donc soit ne pas être `@Transactional` et nettoyer explicitement ses
données en fin de test, soit utiliser
`TestTransaction.flagForCommit()` / `TestTransaction.end()`
(`spring-test`) pour forcer un commit réel avant d'observer l'effet du
listener.

### 1.5 Variables d'environnement

```powershell
$env:DB_PASSWORD="admin"
$env:DOTTEL_KEYCLOAK_ISSUER_URI="http://localhost:8180/realms/dottel-dev"
mvn test
```

`DOTTEL_KEYCLOAK_ISSUER_URI` n'a plus besoin d'être réellement joignable
une fois le `JwtDecoder` de test en place (point 1.1) — mais la propriété
Spring doit résoudre vers une valeur syntaxiquement valide, faute de quoi
le contexte échoue à la résolution du placeholder, avant même d'atteindre
l'auto-configuration. `DOTTEL_JWT_SECRET` n'existe plus (supprimé MM.7,
nettoyé MM.14) — ne pas l'exporter, il n'est lu nulle part.

## 5. Étape 4. RG-08 (le vrai risque) et notifications

```
Ecris les tests 6 et 7.

Flux 6 -- RG-08, le scenario REEL (pas un simple controle de role).
Le risque identifie au Sprint MM.12 n'est pas "deux roles portes par
la meme personne au meme instant" (structurellement impossible, un
utilisateur a un seul role) -- c'est une PROMOTION de role entre deux
etapes d'un meme circuit. Construis ce scenario precisement :

  a) Processus : jeanpaul_mbarga (ARH) valide l'etape ARH d'un
     processus P. ADMIN (marc_tchinda) promeut jeanpaul_mbarga au
     role CRH via PATCH /admin/utilisateurs/{id}/role. jeanpaul_mbarga
     (maintenant CRH) tente de valider l'etape CRH du MEME processus P
     -> 403, SeparationTachesService doit comparer l'ACTEUR (pas
     seulement le role attendu par @PreAuthorize).

  b) Grille : meme scenario sur une grille -- marieclaire_essama (CRH)
     decide EN_ATTENTE_CRH -> DRH -> promue DRH par l'ADMIN -> tente de
     valider la MEME grille -> 403 via SeparationTachesGrilleService.

C'est un test plus exigeant que "meme role sur deux etapes" : il
prouve que la garde-fou survit a un changement de role, pas seulement
qu'un @PreAuthorize bloque un role errone.

Flux 7 -- notifications (MM.13), AFTER_COMMIT. Attention au piege de
la section 1.4 : @MockBean NotificationService, TestTransaction pour
forcer un commit reel (ou test non-@Transactional avec nettoyage
explicite), puis verifie que la validation ARH d'un processus declenche
bien un appel notifier() vers le bon destinataire (le CRH assigne).

Montre chaque test, j'approuve avant d'executer.
```
