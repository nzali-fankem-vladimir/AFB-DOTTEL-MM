## 2. Scénarios de recette par rôle

### Rôle EMPLOYE

- [ ] Se connecter via Keycloak (redirection Authorization Code + PKCE, pas de formulaire local) → retour sur l'application avec un jeton valide
- [ ] Vérifier un matricule éligible → formulaire prérempli, message clair
- [ ] Vérifier un matricule non éligible → message informatif (pas d'erreur rouge)
- [ ] Confirmer l'enrôlement → 201, bénéficiaire visible côté ARH
- [ ] Tenter d'enrôler un matricule déjà enrôlé → 409 avec message clair
- [ ] Accéder à une page ARH → `AccesInterdit` (écran réécrit MM.14 : rôle affiché, bouton de retour vers l'accueil du rôle — pas le `<div>` nu d'origine)

### Rôle ARH

- [ ] Déclencher un processus **normal** pour le mois courant → 201, liste des bénéficiaires
- [ ] Déclencher à nouveau pour le même mois → 409 avec message clair (RG-12, volet normal)
- [ ] Déclencher un **rattrapage** sur une période déjà close → 201 (MM.11 : ce n'est plus un cas d'échec)
- [ ] Ajuster l'état mensuel (exclure un bénéficiaire, modifier une fonction)
- [ ] Valider l'état mensuel → statut passe à EN_ATTENTE_CRH, PDF généré
- [ ] Voir la liste des bénéficiaires, filtrer, modifier, désactiver, exporter — vérifier que les filtres persistent par query params en revenant d'une fiche détail (MM.9)
- [ ] Créer une grille tarifaire → statut initial (vérifier dans le code : EN_ATTENTE_CRH depuis MM.12, pas EN_ATTENTE_DRH comme dans l'original)
- [ ] Consulter l'écran Bénéficiaires en tant que DRH (lecture seule, ajouté MM.14 — voir rôle DRH ci-dessous)
- [ ] Tenter POST/PATCH `/grilles-tarifaires` en tant qu'ADMIN → 403 (ADMIN retiré de ce circuit en MM.14, écart E3)

### Rôle CRH

- [ ] Voir le processus EN_ATTENTE_CRH assigné
- [ ] Tenter de valider en étant le même acteur que l'ARH **après une promotion de rôle** (scénario RG-08 réel, pas un simple contrôle de rôle — voir 7.1 étape 4) → 403
- [ ] Valider en étant un CRH différent → statut passe à EN_ATTENTE_DRH
- [ ] Retourner avec motif → statut RETOURNE, ARH notifiée (vérifier l'arrivée de la notification si `dottel.notifications.enabled=true`, sinon vérifier que le stub ne bloque rien)
- [ ] Voir la grille EN_ATTENTE_CRH assignée (`GET /grilles-tarifaires/en-attente-crh`, MM.12) → décider (valider ou rejeter avec motif) → statut EN_ATTENTE_DRH ou REJETEE

### Rôle DRH

- [ ] Valider le processus EN_ATTENTE_DRH → statut CLOTURE, PDF à 3 signatures, événement de clôture publié
- [ ] Valider une grille EN_ATTENTE_DRH → ancienne grille fermée, nouvelle ACTIVE
- [ ] Rejeter une grille avec motif
- [ ] Consulter l'écran Bénéficiaires en **lecture seule** (ajouté MM.14, écart E2 : route, menu, unités de rattachement visibles — aucune action d'écriture disponible)
- [ ] Consulter l'historique annuel, l'audit
- [ ] Consulter la liste des utilisateurs en lecture seule (`GET /admin/utilisateurs`, alimente le filtre du journal d'audit)

### Rôle ADMIN

- [ ] Créer un utilisateur → 201
- [ ] Désactiver un utilisateur tiers → 200
- [ ] Tenter de se désactiver soi-même → 409 (garde-fou visuel + API)
- [ ] Tenter de désactiver le dernier ADMIN actif → 409
- [ ] Promouvoir/rétrograder un rôle via `PATCH /admin/utilisateurs/{id}/role` → vérifier l'impact immédiat sur `RoleJwtAuthenticationConverter` (le jeton déjà émis reste avec l'ancien rôle jusqu'à son expiration ou un nouveau login — à confirmer en jouant le scénario, pas en le supposant)
- [ ] Créer/désactiver/réactiver une fonction éligible → vérifier que la création passe toujours par `FonctionEligibleService.creer()` avec grille initiale directement ACTIVE (chemin distinct du workflow à trois acteurs)
